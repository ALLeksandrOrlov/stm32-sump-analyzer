# Работа над проектом

## Быстрый старт

```sh
git clone https://github.com/ALLeksandrOrlov/stm32-sump-analyzer.git
cd stm32-sump-analyzer
make docker-build
```

Нужны Git, GNU make и работающий Docker с Buildx. ARM toolchain и QEMU устанавливать
на компьютер не требуется. Результаты находятся в `out/ci/dist`, отчёты —
в `out/ci/reports`. На macOS Docker использует Linux VM (Docker Desktop или Lima).

## Где менять код

- `core/sump_protocol.*`: только wire protocol и метаданные.
- `core/capture.*`: физические параметры захвата, ECA-контроллер, чтение кольца;
  без зависимости от протокола.
- `core/analyzer_app.*`: перевод команд в параметры, проверка флагов SUMP,
  связь контроллера и транспорта.
- `platform/stm32/`: регистры, IRQ, адаптер USB CDC и сборка компонентов.
- `platform/freertos/`: две задачи, MessageBuffer, уведомления и настройки RTOS.
- `third_party/FreeRTOS-Kernel/`: неизменённые исходники закреплённой версии;
  порядок проверки и обновления описан в её [README](third_party/FreeRTOS-Kernel/README.md).
- `Src/`, `Inc/`: только секции `USER CODE`; см. [правила CubeMX](docs/cubemx.md).
- `qemu/`: отдельная модель нужной периферии, не продуктовая прошивка.

Ядро должно оставаться C11 без HAL/USB/FreeRTOS include и динамического выделения памяти.
ISR должны быть короткими: никакого ожидания USB или обработки протокола.
Транспорт приложения копирует принятый пакет. Сам USB заимствует буфер задачи TX
до полного завершения, включая ZLP, либо физического отключения endpoint.
У каждого MessageBuffer должен оставаться один отправитель и один получатель.
Оповещения задач используют индекс 1; индекс 0 занят MessageBuffer.

## Понятный код

У функции должна быть одна проверяемая ответственность. Отделяйте расчёты и
проверку параметров от чтения регистров и других побочных эффектов. Предпочитайте
явные состояния, именованные константы и ранний возврат при ошибке; учитывайте
размерность чисел в именах переменных и ограничивайте время ожидания периферии.

Публичный интерфейс описывает допустимые входы, результат, владение памятью и
контекст вызова: конкретная задача или IRQ. Внутри функции комментарий объясняет
причину ограничения, аппаратный порядок действий или инвариант. Комментарии,
повторяющие следующую строку C, добавляют шум. Документация описывает текущее
поведение и принятые ограничения, а не процесс изменения исходников.

Не добавляйте резервные пути для неподдерживаемых режимов или конфигураций.
Запрос должен либо иметь определённый результат, либо отклоняться до изменения
периферии. Границы модулей нужны для изолированной проверки, а не для дублирования
одного состояния в нескольких местах.

## Проверка изменений

Для быстрой итерации с установленным C-компилятором: `make test test-sanitize`.
Перед отправкой изменений: `make docker-build`. Изменение регистров/IRQ должно
проверяться интеграционными тестами в расширенном QEMU. Изменение модели QEMU
проверяется против того же драйвера STM32 и должно сопровождаться описанием
поддержанного поведения и ограничений.
Изменения очередей, уведомлений и жизненного цикла USB проверяются через
`make qemu-rtos-test QEMU=/path/to/patched/qemu-system-arm`: два тестовых ELF
исполняют настоящее ядро FreeRTOS на Cortex-M4F. Один управляет тестовыми портами,
другой соединяет задачи с настоящим драйвером захвата и отложенным IRQ.

Выбирайте тест по контракту, который может нарушиться: чистый расчёт проверяется
нативно, работа регистров и прерываний — в QEMU, временные и электрические
характеристики — на плате. Тест воспроизводит входное условие, выполняет действие
и проверяет наблюдаемый результат. Не копируйте алгоритм реализации в ожидаемый
результат и не привязывайте проверку к внутреннему порядку вспомогательных вызовов,
если этот порядок не является частью контракта. Подробности и приоритеты —
в [методике тестирования](docs/verification.md).

В PR укажите:

- какую проблему решает изменение и как меняется поведение;
- какие проверки выполнены;
- есть ли изменения протокола, таймингов или требований к плате;
- какие проверки ещё требуют реального устройства.

Результаты сборки хранятся в игнорируемом `out/`. Генерируемые CubeMX `Makefile`
и каталог `build/` также исключены из Git. Не обновляйте эталон CubeMX автоматически,
чтобы случайные изменения генерируемого кода не становились «разрешёнными».
